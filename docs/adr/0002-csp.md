# ADR-0002: Content-Security-Policy strategy and rendering model

- Status: **Accepted** (2026-10-27, owner decision: option B)
- Date: 2026-10-27
- Deciders: owner

## Context

RULES §10.4 requires security headers and "a strict CSP (no `unsafe-eval`)". SPEC §11 says the CSP should use a
nonce or hashes. SPEC §1 and §12 want pages statically generated wherever possible, and SPEC §12 sets
Lighthouse budgets for LCP/TBT that favour static HTML served from a CDN.

These goals conflict. Next.js injects small inline scripts into every HTML document (bootstrap and streaming
data). Without `'unsafe-inline'`, the browser blocks them unless each carries a per-response nonce. A nonce must
be generated per request, which means every route is rendered dynamically and cannot be served as a static file.

## Options

### A. Nonce-based CSP through `proxy.ts`

- `script-src 'self' 'nonce-<random>' 'strict-dynamic'`, nonce generated per request in `src/proxy.ts`.
- Strongest protection against injected scripts.
- Forces dynamic rendering of **all** routes: no static prerendering, no CDN page caching, `generateStaticParams` loses most of its value, higher TTFB and server cost. Puts the LCP/TBT budgets at risk.

### B. Static generation with `script-src 'self' 'unsafe-inline'`, no `unsafe-eval`

- Pages stay static; headers are set in `next.config.ts`.
- `'unsafe-inline'` weakens the defence against injected inline scripts. Mitigations in this codebase: no `dangerouslySetInnerHTML` except the escaped JSON-LD helper (RULES §10.3, enforced by the `react/no-danger` lint rule), no user-generated content, no third-party scripts, strict `default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`.
- Compatible with the performance budgets and Vercel static hosting.

(Hash-based `script-src` is not practical: Next.js inline script contents change per build and per page.)

## Decision

**Option B.** Everything is statically generated. The CSP is built in `src/lib/security-headers.ts` and applied
from `next.config.ts`: `script-src 'self' 'unsafe-inline'`, `style-src 'self' 'unsafe-inline'`, `default-src 'self'`,
`frame-ancestors 'none'`, `upgrade-insecure-requests` in production. `'unsafe-eval'` is added in development only
(React's dev runtime needs it) and never in production; a unit test and an e2e assertion enforce this.

Currency must still reach the first HTML without making pages dynamic, so it is applied through a hidden route
segment:

- Routes live under `src/app/[locale]/[currency]/...`; `generateStaticParams` returns locale x currency (x slug).
- `src/proxy.ts` runs the next-intl middleware, then reads the `hc_currency` cookie (`USD|THB`, default by locale:
  `en` -> USD, `th` -> THB) and **rewrites** the public URL `/en/shop` internally to `/en/usd/shop`.
- Public URLs never contain the currency. A direct request to an internal `/{locale}/{usd|thb}/...` path is
  redirected to the public URL.
- Switching currency sets the cookie and calls `router.refresh()`.
- The proxy only rewrites; it sets no nonce and adds no per-request state to the HTML, so the pages remain
  static and CDN-cacheable.

## Consequences

- All routes stay static and cacheable, which keeps the Lighthouse budgets reachable.
- The script policy is weaker than a nonce policy. This is the known, accepted residual risk. It is limited by the mitigations listed under option B and by lint rules that ban `dangerouslySetInnerHTML` outside `src/components/seo/json-ld.tsx` and ban React, Next.js, Node I/O and browser globals inside `src/lib`.
- Static output multiplies by the number of currencies (2) for every locale x slug combination; build time and output size grow accordingly.
- T03 implemented `src/proxy.ts` and the `[currency]` segment, with unit tests for the cookie -> currency default, the rewrite, the redirect away from internal paths and the matcher. Details and trade-offs are in ADR-0003.
- Revisit only if the owner later wants a stricter script policy: that would mean option A and a new ADR.
